# Agent Note: Supervised terminals as a plugin, not as loop machinery

Status: implemented

[English](2026-10-06-supervised-terminal-plugin.md) | 中文

## Problem

一个启动长时间无人值守运行的模型，需要有人发现运行何时不再推进：API 连接断开、速率限制把 CLI 停住、确认弹窗永远在等、或者 agent 在原地打转。harness 已经能持久化对话、也能在 PTY 里托管别的 CLI，但没有人看着这些终端，也没有把无人值守运行所需的任务计划、恢复点和证据持久到能扛住中断。

最顺手的形态是把机制塞进循环——在 `agent-loop` 里加一个监工阶段，或者加一个新的 guard 去检查每次工具调用。那会在模型之外再放一个决策者，并让 harness 承担它无法给出依据的判断。

## Decision

把这个能力做成一个可选的 profile bundle `@deepseek-ai/dsh-supervisor`：它在 harness 已经打开的终端里托管其他 CLI agent、产出关于这些终端的确定性证据，并持久化被中断的运行所需的一切。监工模型留在 harness 循环里做判断；没有任何组件做判断、调用模型、或改动 `agent-loop`。

`supervisor-core/src/index.ts` 注册核心插件与看门狗；各组件自己的 `src/tools.ts` 拥有 19 个面向模型的工具；`supervisor-core/src/runtime.ts` 持有解析后的配置，以及所有终端工具汇入的唯一一条结算流水线（结算走 `observe`，普通读取走 `inspect`，后者绝不能推进心跳或追加输出日志）。

## 六个组件、一个 bundle

这项能力覆盖了几件生命周期并不相同的关切：终端之上的实时控制面、可持久化的任务记录、偏调度形态的编排、面向成本与人的运维、监工 agent 自身失败请求的自动起搏，以及运行结束后的自动关机。它们作为**一个**可安装单元交付，因为操作者想要的是整套控制面而不是散装管道；它们又各自独立成包，因为每个组件都能被单独开关、单独配置、单独呈现：插件管理器列出的是一个 bundle 与它下面的六个组件，每个组件有自己的标题、简介、图标与启用开关，而 profile 补丁可以配置或关闭某一行而不必重述它的兄弟行。

这次拆分同时也是接缝决策。`supervisor-core` 发布 `ctx.supervisor`，提供会话、检测输出、心跳、输出日志与计划存储；`supervisor-tasks` 发布 `ctx.supervisorTasks`，提供断点、工单与 git 操作；`supervisor-ops` 发布 `ctx.supervisorOps`，提供预算账本、聊天通道与关机门禁。计划、编排、运维、起搏与关机五个组件消费这些服务，而不是互相导入对方的模块，因此再增加一个组件的成本是一个包、bundle 的 `cordis.patch.yml` 里一行 `insert`、以及 `dependencies` 里一条。配置遵循同样的规则：被两个组件读取的路径或阈值放在核心，各组件统一从 `ctx.supervisor.config` 读取；只由某一个组件读取的设置留在它自己的 `Config` 模式里。这正是为什么 profile 里那块 `- id: supervisor` 只需配置一次共享状态目录，而其余各行都以默认值加载。

## Detection stays literal

L1 检测是 `src/guard.ts` 与 `src/adapter.ts` 里的固定字面量匹配表。配置可以停用某条规则、改严重度、或提供字面量关键词；但永远不能提供正则表达式，因为运维或模型给的模式会带着自己的开销进入每一次扫描。按 agent 的输出分类同理：每种被托管 CLI 一套字面量模式，其中 waiting 优先于 active、active 优先于 error、completion 排最后，这样活跃的提示符不会被误读成对话本来就在处理的失败。

两个确定性计数器接手了模型本来必须记住的东西：按会话比较"输出未变化"的进度熔断器，以及按任务统计已记录 token 花费的预算账本。两者都不采取行动：它们是附在工具结果上的证据，行动始终属于监工模型。

看门狗是唯一不经工具调用就能触达模型的路径：被托管终端心跳过期时它 steer 持有者，解析出的限流恢复时刻到点后再 steer 一次。其余一切都等模型来问。

## Durable records, and what a checkpoint excludes

一个状态目录保存自描述 JSON：任务计划、断点、审查问题单、技能清单、每终端输出日志、心跳与交付报告。每个文件脱离插件也能读，因此续跑——或人——都能重建状态。

`supervisor_checkpoint` 提交的是代码，不是状态。它移动 `supervisor/<taskId>` 分支、用 `git add -A` 暂存，并在状态目录与 worktree 根位于仓库内部时把它们排除，因为恢复执行 `git reset --hard`：一旦状态目录进了提交，用较旧的断点恢复就会删除所有更新的计划、断点与问题单。

不发布 invariant 伴随包。本包给出的每一项结论要么是持久化记录，要么是从单次结算推导出的值，消费者可以用相同输入重新推导，不存在需要交叉验证的独立观测；包 README 记录了这一理由。

## Isolation, review, and the chat seam

并行子任务各自获得一个 git worktree，集成按依赖顺序合并它们的分支并在第一次冲突处停止；合并保持串行而不是并发抢跑。审查是交给模型判断的材料包——计划、验收标准、断点、diff、终端尾部——其中的 findings 变成一张带重试预算、到点自动升级的问题单。

聊天面是接缝，路由归插件：部署方提供线路（`ChatTransport`），`useChatTransport` 在没有处理器时自行路由入站消息——升级问题的回答回到发问的 agent，其余消息 steer 给受管终端各自的持有者（去重）。需要不同路由的部署传入自己的处理器，接管这两件事。

## Alternatives considered

- **在 `agent-loop` 或新 guard 里做监工** —— 那会让循环承担关于另一个 agent 健康状况的判断，并且所有部署都被迫背着它。做成插件让监工保持可选，循环的契约分毫不动。
- **让配置提供 L1 正则表达式** —— 最灵活的表，也是每次扫描每份结算时的灾难性回溯风险。字面量模式加上可配的严重度与关键词，覆盖了同样的运维需求。
- **持久化滑动窗口与熔断器计数** —— 持久的计数能让重启后的 harness 接着算停滞次数，代价是每次结算写一个文件、外加一份要迁移的 schema。平台自身的 repeat-tool-reminder 把窗口放在内存里；这里跟随它，重启后重新观察。
- **连状态目录一起提交整个工作区** —— 恢复状态会随分支一起走。但恢复时的 `git reset --hard` 会删掉更新的记录，因此状态目录留在磁盘上、不进提交。
- **把飞书传输内置** —— 部署少一步，但 harness 要持有某个厂商线路的凭证并跟进它的变更。改为提供接缝加路由；想要飞书的部署自己接 SDK。
- **保持单体一个包** —— 一行、一份 `Config` 模式、一份 README，也没有跨包的服务面。但它同时会让所有组件的工具只能一起开关，让插件管理器里的唯一组件重复 bundle 自己的名字与简介，并且把将来每一次新增都塞进同一个包的覆盖率与评审面。
- **发布 invariant 伴随包** —— 它只能复述存储记录或推导值，而这些正是存储与结算流水线已经在检查的东西。

## Consequences

本插件与终端后端、工具运行时并排挂载，没有 `terminal_open` 的装配用不了它：它从不自己打开终端，因此会话只有一个创建者。六个组件合计 19 个工具 schema 会在加载期间进入每个请求，这是自带控制面的代价；由于每个组件都是独立的行、拥有自己的工具，想要更少的部署只需关掉持有这些工具的那个组件。

换来的是一条留下证据的无人值守运行：标记、命中、分类、熔断器状态、预算、计划、问题单，以及由 git 钉住的恢复点——既给做判断的模型读，也给早上回来的那个人读。
