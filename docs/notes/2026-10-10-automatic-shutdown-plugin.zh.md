# Agent Note: 把自动关机做成 supervisor bundle 的第 6 个组件

Status: implemented

[English](2026-10-10-automatic-shutdown-plugin.md) | 中文

## Problem

运维组件交付了关停闸门——运维方的 `enabled`、`command` 与 `gracePeriodMin`，以及判断某个触发条件是否允许所配置命令的 `supervisor_shutdown`——却没有任何东西对"允许"的决策采取行动。03:00 结束的运行会让机器一直开着，直到有人回来，因为唯一知道工作已经结束的组件只能回答问题，别的什么也做不了。

## Decision

把 `@deepseek-ai/dsh-supervisor-shutdown` 做成 bundle 的第 6 个组件：一个函数插件，注册 `supervisor_power`，在监工服务旁注入 `ctx.shell`，由它拥有执行，而闸门仍归 `supervisor-ops` 所有。

这个拆分是刻意的。部署方可能想要用量预算、交付报告与关机决策，却不想让任何插件拥有把机器关掉的权力；而策略本就该留在运维配置已经所在的地方——在 executor 旁边重新声明 `enabled`、`command` 与 `gracePeriodMin`，会让同一个运维设置有两个归属。组件绝不发明操作系统命令：它经 `ctx.shell` 运行闸门返回的命令，受所配置的 `commandTimeoutSec` 约束，而拒绝结果根本不带命令。它沿四条已配置路径武装该命令——`scheduleAt` 墙钟、`scheduleAfterMinutes` 或 `scheduleAfterSeconds` 倒计时、在每份已存计划的子任务都为 `completed` 或 `skipped` 时触发的 `watchPlans` 监视器，以及 `idleTimeoutMin` 空闲时段——另有模型自身经 `supervisor_power` 发出的请求。

闸门是在尝试触发时被询问，而不是在尝试武装时。在武装时询问会把"仍在宽限期之内"变成拒绝，于是刚刚完成的计划集合永远无法武装；在触发时询问，同一状态则是"尚未"。

另外两条规则让这套执行可以安心地一直挂着。即使本组件什么都没武装，`cancelCommand` 也会运行，因为更早的一次运行可能给操作系统留下了它自己的关机定时器，而只有运维方的这条取消命令能停下已经在倒计时的机器。并且，一次已触发的尝试会消费掉它的条件——计划监视器在未重新打开工作前不会重新武装同一组已完成的计划，空闲触发的尝试会重置空闲时钟——因此关机命令不会为已经触发过它的那个条件重复执行。

## Alternatives considered

- **把执行放进 `supervisor-ops`。** 包从两个变成一个，闸门可以直接运行自己的命令。它也会让每个运维部署——预算、报告、聊天——都能把机器关机，并把"回答"的组件与"行动"的组件合成一个。
- **由插件自行选择平台关机命令。** 无需运维配置即可工作，代价是硬编码一个 `shutdown` 调用，去猜平台、猜权限、猜运维方的意图；整套安全模型的前提正是由运维方指名命令。
- **在武装时询问闸门。** 一次尝试会立刻知道它究竟能否触发。它也会让在宽限期内武装的尝试变得不可能，把"尚未"当成"拒绝"。
- **只在本地已武装时才取消。** 更简单，代价是上一次运行启动的操作系统定时器在本组件里没有任何手段停下；而运维方的取消命令是停下已在倒计时机器的唯一办法。
- **照搬参考应用的 GUI 倒计时浮层、托盘提醒与单实例互斥。** 这些部件服务于桌面外壳：人类盯着的窗口、可以点击的图标、对第二个应用副本的检查。本组件所服务的运行是无人值守的，而聊天提醒已经把截止时间送到了人所在的地方；无论有没有窗口显示，要调度的时刻都不会变。

## Consequences

无人值守的运行现在可以以"机器已关机"收尾，而不是等人回来。代价是运维方命令会带着 harness 的权限运行：它由双重开关（组件自身的 `enabled` 与闸门的 `enabled` 及命令）、触发时的闸门、只报告不执行的干跑模式，以及 shell 到点杀死命令的每命令超时共同约束。
